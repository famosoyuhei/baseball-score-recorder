# 18通りシミュレーションテスト計画

## 目的

記録粒度、記録レベル、観戦環境の全組み合わせで、試合進行・UI表示・保存復元の破綻を検出する。

## モード軸

| 軸 | 値 |
|---|---|
| recordingLevel | `inning` / `batter` / `pitch` |
| detailLevel | `basic` / `standard` / `detailed` |
| recordingMode | `bench` / `tv` |

## 共通期待値

- 試合を開始できる
- 選択したモードが `game` に保存される
- `#gameScreen` に記録粒度のCSSクラスが付与される
- 入力可能な情報と表示される情報がモードに合う
- 保存後に復元できる
- 復元後のスコア、アウト、走者、カウントが一致する
- 例外で画面が停止しない

## テストシナリオA: 最小試合進行

1. 試合を開始する
2. 1回表を3者凡退で終了する
3. 1回裏を1得点で終了する
4. 保存する
5. 再読み込みする
6. 保存済み試合を復元する
7. スコアとイニング状態を確認する

## テストシナリオB: 走者責任

1. 先頭打者が四球で出塁する
2. 投手交代する
3. 次打者が安打で一三塁にする
4. 次打者が内野ゴロで一塁走者アウト、打者走者出塁
5. 責任走者が期待通り移るか確認する
6. 保存復元後も責任投手が保持されるか確認する

## テストシナリオC: 打席途中投手交代

1. 打者のカウントを2ボール以上にする
2. 投手交代する
3. 四球で出塁させる
4. 打者走者が旧投手責任になることを確認する
5. 同じ手順を1ボール以下でも行い、新投手責任になることを確認する

## テストシナリオD: YouTube動画連動操作密度

1. YouTube動画連動シミュレーションを有効にして試合を開始する
2. 対象動画URLを読み込む
3. 任意の10秒区間を選ぶ
4. その区間で必要な記録操作を実施する
5. 操作ログと動画時刻メモを保存する
6. 10秒あたりの操作数を集計する
7. `docs/rules/youtube-operation-density.md` の基準で実用性を判定する
8. 対応するボタン操作がない未対応プレーで前に進めない事態が起きなかったか確認する

判定の観点:

- 未対応プレーで記録が停止した場合は、操作密度に関係なく不合格/P1
- リアルタイム入力できるか
- 一時停止・巻き戻し前提なら実用可能か
- 操作密度が高い原因はルール複雑性か、UI手数か
- 記録粒度を下げるべきか
- UI改善で操作数を削減できるか
