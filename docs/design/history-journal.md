# 履歴ジャーナル設計メモ ―「戻る・進む」のブラウザ式化

- 作成: 2026-11-19（第1段：設計と棚卸し）
- 状態: 2026-11-19 に Yuhei が未決事項1〜3を決定済み（末尾参照）。残る未決は上限（実測で判断）のみ
- 関連: `docs/product/competitor-undo-redo-research.md`（競合調査）、`docs/product/competitor-swot.md`

## 1. 背景と目的

発端は実務要件：**ビデオ判定で3アウト（や試合終了）が覆ったとき、記録員は瞬時に一つ前に戻して再記録しなければならない**。

2026-11-19 の修正で、3つの記録レベル（半イニング／1打席／1球）すべてが「1ステップだけ」境界を越えて戻れるようになった。しかし現状の取消はレベルごとに別機構で、「進む（Redo）」は存在せず、履歴は打席単位を除きメモリ上のみ（再読み込みで消失）。

商品化を見据え、ブラウザの戻る・進むと同じ感覚で **何ステップでも戻れて、進めて、再読み込みしても残る** 統一機構（履歴ジャーナル）に作り替える。副次効果として、試合中のクラッシュから「最後の操作直前」まで復旧できることも売りになる。

## 2. 競合コンベンション（採用／見送り）

詳細は競合調査ドキュメント参照。要点と本アプリでの判断：

| 競合の流儀 | 出典 | 判断 |
|---|---|---|
| Undo/Redo は記録画面に常時表示、Undo の隣に Redo | GameChanger | **一部採用**（2026-11-19 Yuhei決定）。Redo は「進める時だけ」Undo の隣に現れる。常時表示はしない。あわせて一般原則として、**選択できないボタンはすべて非表示**にする（ボタンが多すぎるため。無効表示で残さない） |
| Undo は投球単位で複数ステップ、試合終了後でも戻って再記録できる | iScore（公式 FAQ） | **採用**。本設計の中核 |
| Redo はブラウザ式：新しい入力をした瞬間に Redo は破棄され、その旨を明示 | GameChanger（公式警告文） | **採用**。仕様として明文化し、UI でも「進む」ボタンが消えることで示す（非表示原則） |
| 過去プレーの直接編集では「帰結を変える変更」（アウト⇔セーフ）を禁止し、覆しは Undo＋再記録に一本化 | iScore | **採用**。本アプリの `correctAtBat` の許容範囲もこの原則で見直す（第3段） |
| 訂正は3層（Undo／帰結が同じ編集／数値の直接上書き＋プレーバイプレーへの注記） | 両アプリ共通 | **採用**（2026-11-19 Yuhei決定：直接編集もやる）。第1期は Undo/Redo に集中し、直接編集は第3段で実装する。対象にはワイルドピッチ⇔パスボールのような、走者・アウト・得点の帰結は同じでも個人成績（投手・捕手の責任、自責点等）に影響する分類訂正を含む。直接上書きは既存のイニング数値入力（recordInningData）が相当するが、注記を残す仕組みは将来課題 |
| ファイナライズ後も再開して訂正→再ファイナライズ可能 | 両アプリ | **採用・確定**（2026-11-19 Yuhei決定：確定後も編集可能にする）。試合確定後もジャーナルを残し、戻って／直接編集で訂正して再確定できるようにする。理由：ワイルドピッチ判定が後からパスボールに変わる等、個人成績に影響する訂正が試合後に発生しうるため |
| 守備側の編集は後方伝播、攻撃側は単一プレー | GameChanger | 将来の直接編集（第2層）で採用を検討。今期は対象外 |
| クラウド同期を前提にした履歴保持 | GameChanger | **見送り**。本アプリの勝ち筋はオフライン・軽量（SWOT）。履歴は端末内 IndexedDB に保持する |

## 3. 現状の取消機構（棚卸し）

| 機構 | 単位 | 永続性 | 備考 |
|---|---|---|---|
| `pitchActionHistory`（app） | 投球／走者プレー1件 | メモリのみ | 打席ごとにクリア。2026-11-19 に境界越え対応（`undoBaserunningPlay` / `undoCompletedAtBatLastPitch`） |
| `inningActionHistory`（app） | イニング内操作1件 | メモリのみ | 2026-11-19 に「イニング終了」も対象化（`reopenHalfInning`） |
| `undoLastAtBat`（gameManager） | 打席1つ | 打席記録が残る限り可 | `gameStateBefore`＋全打席再計算。複数回遡れる唯一の機構 |
| `_endHalfInningSnap`（app） | ハーフ終了1回 | メモリのみ | 確定待ち画面の「戻す」用 |
| `correctAtBat` / `deleteAtBat`（gameManager） | 打席の訂正・削除 | 訂正履歴を別途記録 | 過去プレー編集の既存実装。許容範囲の原則は未整備 |

ジャーナル導入後は、上記のうち「戻る」系はジャーナルのフロントエンドに置き換える（ボタンは残し、エンジンを差し替える）。

## 4. 状態変更の入口一覧（ジャーナルの捕捉対象）

| `recordAtBatResult` | 球ごと：打席完了フォーム／打席：結果入力 | 単一 | 内部で `endHalfInning`→`startInning`／`endGame` まで進みうる |
| `recordAtBatQuick` | クイック記録 | 単一 | |

## 5. ジャーナル設計

### 5.1 モデル

**操作単位のエントリ＋「前状態スナップショット」＋「記録 ID 集合による突き合わせ復元」** を採る。

- 各ユーザー操作の**直前**に、メモリ上の集約状態（Game／現在の Inning／現在の AtBat／打順）と、その時点でストレージに存在する当該試合の記録 ID 集合（innings／atBats／pitches）をエントリとして保存する。
- **戻る**：エントリの前状態を復元し、ID 集合に無い記録（その操作以降に作られた記録）をストレージから削除する。操作の種類に依存しないため、複合操作や将来の新操作でも同じ手順で戻せる。2026-11-19 に直した「幽霊イニング」型の復活も、ID 突き合わせで構造的に防げる。
- **進む**：戻る際に退避した「離脱時の状態」を同様に復元する（Redo スタック）。**新しい操作を記録した瞬間に Redo スタックを破棄**する（ブラウザ式、GameChanger と同じ仕様を明示）。
- エントリには表示用ラベル（操作種別＋対象）を持たせ、ボタンのツールチップ／ラベルに使う（例：「取消：盗塁成功」）。

### 5.2 エントリ構造（案）

```
{
  gameId, seq,            // 試合内連番
  label: { type, detail },// 'pitch' | 'atBatResult' | 'baserunning' | 'inningAction' | 'endHalfInning' | 'substitution' | ...
  createdAt,
  before: {
    game: <Game JSON>, currentInning: <Inning JSON|null>, currentAtBat: <AtBat JSON|null>,
    currentBattingOrder: { home, away }, isRecording
  },
  recordIds: { innings: [id...], atBats: [id...], pitches: [id...] }
}
```

Redo 側は「離脱時の状態」を同じ形で保持する（before を after として読み替える）。

### 5.3 フック方式（捕捉の実装方針）

- GameManager の対象メソッド冒頭で捕捉するのを基本とし、入口を一元化する（UI が変わっても漏れない）。
- 複合操作は app 側のハンドラ冒頭で捕捉を開始し、内部の GameManager 側捕捉は**入れ子として外側のエントリに合流**させる（捕捉中フラグ＋深さカウンタ）。
- 捕捉は「操作が成功した場合のみ確定」する。例外時はエントリを破棄し、状態は操作側のエラー処理に従う。
- 既存の取消機構（`undoLastAtBat` 等）はジャーナル経由の復元に置き換える。ただし `undoLastAtBat` の再計算は統計整合の安全網として残すかは第2段で判断する。

### 5.4 永続化

- IndexedDB（`BaseballScoreDB`、現行 version 1）に新ストア `history` を追加し、**version 2 へ移行**する。ストアは `gameId` インデックス＋試合内 `seq` で引ける形にする。
- 容量見積もり：1エントリは前状態 JSON（選手・統計を含む Game 本体が大半）＋ID 集合で概ね 10〜25KB。1試合300投球規模で約 3〜7MB。IndexedDB の実用上限に対して十分小さい。
- 保持方針：試合データと同寿命（試合を削除したらジャーナルも削除）。**確定済み試合でもジャーナルは残し、編集可能とする**（2026-11-19 Yuhei決定）。
- 既存の試合データ（ジャーナルなし）で開いた場合は、ジャーナルを空から開始する（移行処理は不要）。

### 5.5 既存ボタンとの対応

| 現在のボタン | ジャーナル導入後 |
|---|---|
| 前プレー取消（球ごと） | ジャーナルを1ステップ戻る |
| 前打席に戻す（打席・球ごと） | 直前の打席開始境界までジャーナルを繰り返し戻る |
| 取消（イニング） | ジャーナルを1ステップ戻る |
| （新規）進む | ジャーナルを1ステップ進める。**進める時だけ、対応する取消ボタンの隣に現れる**（2026-11-19 Yuhei決定）。進めない時は非表示 |
| 試合終了画面の「戻す」 | ジャーナルを1ステップ戻る（確定待ちの取消） |

ボタン表示の一般原則（2026-11-19 Yuhei指示）：**選択できないボタンはすべて非表示にする**。見えているボタンが多すぎるため、無効（disabled）状態で画面に残さない。ジャーナル関連ボタンはこの原則で実装し、記録画面全体のボタンへの適用は第4段で棚卸しして行う。

## 6. 段階計画

- **第2段（核）**：`history` ストアと GameManager 側の捕捉・復元 API を実装。球ごと・打席単位の入口に接続し、既存の取消ボタンのエンジンをジャーナルに差し替える。「進む」はこの段では内部 API のみ。
- **第3段（全面接続＋直接編集）**：イニング単位・交代・確定・コールド等、残りの入口を接続。確定済み試合の再開・訂正・再確定を可能にする。過去プレーの直接編集（第2層）を実装する：`correctAtBat` の許容範囲を「帰結を変えない」原則で明文化し、ワイルドピッチ⇔パスボール等の個人成績に影響する分類訂正を含める。アウト⇔セーフ等の帰結変更は引き続き Undo＋再記録に一本化する。
- **第4段（UI と永続化の仕上げ）**：「進む」ボタンを、進める時だけ取消の隣に表示（4言語 i18n 込み）。あわせて記録画面のボタンを棚卸しし、**選択できないボタンはすべて非表示**にする原則を適用する。再読み込み後の履歴復元、古い試合のジャーナル整理。

## 7. テスト戦略

- 実物の `data.js`／`game.js` を Node 上で動かすハーネス（2026-11-19 の修正で確立した方式）を拡張し、**操作列 → 任意の地点まで戻る → 進む → 状態が完全一致**を機械検証する。
- 代表シナリオ：ビデオ判定パターン（1回表2アウト1,3塁、フォースアウトでチェンジ→覆って内野安打＋1点）を全レベルで往復させる。
- 復元後にストレージへ幽霊記録が残らないこと（ID 突き合わせ）を必ず検証する。

## 8. 決定事項と未決事項

2026-11-19 に Yuhei が決定：

1. **確定済み試合も編集可能にする**。ジャーナルは確定後も残す。理由：ワイルドピッチ判定が後からパスボールに変わる等、個人成績に影響する訂正がありうる。
2. **「進む」は選択可能な時に、取消の隣に現れる**。あわせて一般原則として、**選択できないボタンはすべて非表示**にする（見えているボタンが多すぎるため）。
3. **過去プレーの直接編集（第2層）をやる**。第3段で、`correctAtBat` の「帰結を変えない」範囲を明文化したうえで実装する。ワイルドピッチ⇔パスボール等の分類訂正を含む。

未決：

4. ジャーナルの上限（ステップ数・容量）に制限を設けるか。当面は無制限＋実測で判断する想定。
